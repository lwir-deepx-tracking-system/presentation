02. 사용자가 할 일은, 한 사람을 고르는 것

사용자가 하고 싶은 일은 여러 명 중 한 사람을 고르는 것입니다. 왼쪽은 팀이 제공한 녹화 재생 화면입니다. 사람마다 박스와 번호가 붙어 있습니다. 이 화면은 실제 옥상에서 짐벌이 추종한 장면은 아닙니다. 목표 운용에서는 먼저 사람이 검출되고, 사용자가 그중 하나를 선택하면 같은 ID의 위치를 제어기로 전달합니다. 사용자는 화면에서 선택 상태와 추종 상태를 보고 필요하면 수동으로 바꾸거나 정지할 수 있어야 합니다. 그래서 저희가 풀어야 할 문제도 세 가지였습니다. 사람을 제대로 찾는 것, 가려져도 같은 사람으로 이어가는 것, 그 결과에 카메라가 제때 반응하는 것입니다.

04. 보드에서 판단하고, 짐벌로 움직인다

카메라가 사람을 따라가려면 영상에서 얻은 위치가 실제 장치 명령까지 이어져야 합니다. 영상은 카메라에서 보드로 들어오고, 보드에서는 NPU로 사람을 검출한 다음 추적기가 이전 프레임의 ID와 연결합니다. 그중 사용자가 선택한 ID의 위치를 제어 브리지로 넘기면 짐벌이 좌우와 상하 방향으로 움직입니다. 짐벌이 움직이면 다음 영상에서 표적 위치가 달라지고, 그 위치를 다시 계산합니다. 이렇게 같은 흐름이 반복됩니다. 아래의 PC 웹 GUI는 이 흐름을 보고 개입하는 창입니다. 표적을 고르고, 연결 상태와 영상을 확인하고, 필요하면 수동으로 움직이거나 정지합니다. 구현에서는 기존 C++ 카메라 수신과 제어 코드를 활용하고, Python 추적 서버와 웹 화면을 연결했습니다. 그래서 모델 결과를 잘 만드는 것만큼 각 프로그램 사이에서 위치와 상태를 일관되게 전달하는 것도 중요했습니다.

05. 멀고 작은 사람도, 찾아야 한다

첫 번째는 사람을 찾는 문제입니다. 화면에서 작게 보이는 사람이나 일부가 가려진 사람도 검출되어야 다음 단계로 넘길 수 있습니다. 왼쪽은 팀이 제공한 실제 야외 라벨링 작업 화면입니다. 열화상에서는 옷의 색 대신 밝기와 윤곽을 보고 사람 상자를 정해야 하므로, 데이터의 상자 기준을 맞추는 작업부터 필요했습니다. 검출기는 사전학습 가중치에서 출발해 FLIR 열화상으로 전체 파인튜닝했습니다. 실제 m급 학습 기록에는 학습 영상 10,491장, 검증 영상 1,144장과 30 epoch가 남아 있습니다. 여기서 중요한 것은 학습을 오래 했다는 사실보다, 고정한 검증셋에서 사람이 더 잘 검출되는지 확인하는 것입니다. 학습 곡선과 학습 방식별 비교는 예비자료에 남겼습니다. 이 학습 기록을 보드에서 측정한 INT8 성능과 바로 같은 점수로 취급하지 않고, 다음 단계에서는 장치 실행 시간까지 함께 확인했습니다.

06. 더 잘 찾는 모델, 더 빨리 도는 모델

검출 모델은 정확도와 실행 시간을 함께 봤습니다. 이 결과는 11월 6일 DX-M1에서 FLIR 여덟 영상, 3,749프레임을 평가한 각 모델 한 번의 비교입니다. 사람 AP는 YOLO26s가 42.32퍼센트, m이 45.79퍼센트로 m이 3.47퍼센트포인트 높았습니다. 반면 NPU 호출 중앙값은 s가 19.02밀리초, m이 27.12밀리초였습니다. 이 비교에서는 m이 더 정확한 대신 호출이 8.10밀리초 길었습니다. 다만 두 모델은 학습 이력도 달라 모델 크기만이 원인이라고 볼 수는 없습니다. 또 이 결과가 지금 옥상에서 비교할 두 후보의 결과라는 뜻도 아닙니다. 이 슬라이드는 모델 선택에서 확인했던 정확도와 시간의 절충을 보여줍니다. 최종 운용 모델은 옥상에서 두 후보를 같은 조건으로 비교한 뒤 확정합니다.

07. 가려졌다 돌아와도, 같은 사람인가?

추적은 이번 프레임의 사람이 앞 프레임의 누구인지 연결하는 작업입니다. 그림의 ID 12번을 사용자가 골랐다고 생각해 보겠습니다. 다른 사람이나 장애물 뒤로 잠깐 가려졌다가 다시 나타났을 때 12번으로 이어져야 사용자의 선택도 유지됩니다. 여기서 다른 번호가 붙으면 사람을 다시 검출했더라도 선택한 표적과의 연결은 끊깁니다. 기존 추적에서는 가려진 동안 예측 위치가 실제 움직임에서 벗어나면, 다시 나타난 사람과 연결하지 못하는 문제가 있었습니다. 저희는 실제 관측된 이동 방향과 마지막 위치를 더 활용하는 OC-SORT를 비교했습니다. 다시 관측됐을 때 놓친 구간의 상태도 갱신해 연결을 보완합니다. 이 그림은 그 문제를 설명하는 개념도입니다. 알고리즘을 바꾼 효과는 검출 결과를 같게 고정한 다음 번호가 바뀐 횟수와 신원 연결 지표로 확인했습니다.

[전환] 같은 검출 결과에서 추적기만 바꿔 비교했습니다.

08. 번호가 바뀌는 횟수를 줄였다

같은 YOLO26s 검출 결과로 Orange Pi에서 ByteTrack의 최선 조합과 조정한 OC-SORT를 비교했습니다. 번호가 바뀐 횟수는 2,964회에서 775회로 줄었습니다. 약 73.9퍼센트 감소입니다. 신원 연결을 평가하는 IDF1도 49.56에서 64.10퍼센트로 높아졌습니다. 번호를 유지하려고 아예 사람을 출력하지 않아도 번호 변경 수는 줄 수 있기 때문에, 누락과 헛출력도 함께 봤습니다. 공식 기본값을 그대로 썼을 때는 누락이 많았고, 열화상 검출 점수에 맞게 기준과 출력 규칙을 조정해 비교했습니다. 이 결과는 자체 녹화 18개 시퀀스에서 얻은 개발 비교입니다. 새로운 현장의 성능이나 실제 짐벌 추종 성공률을 뜻하지는 않습니다. 이후의 PC 옵션 비교와 전체 원표는 예비자료에 두었습니다. 여기서의 핵심은 같은 검출을 놓고도 연결 방법을 바꾸면 선택 표적을 더 일관되게 유지할 수 있었다는 점입니다.

[전환] 이제 맞는 결과를 제때 전달해야 합니다.

09. 빠른 추론만으로는, 제때 반응하지 못한다

추적 결과를 제때 얻으려면 모델 호출뿐 아니라 다음 입력을 언제 준비하고 제출하는지도 중요합니다. 김재남 팀원의 별도 C++ Runtime 시험에서는 실제 NPU를 사용하면서 입력만 메모리 재생으로 바꿔 충분한 부하를 만들었습니다. 초당 60장 입력에서 미완료 요청 상한이 1일 때 약 50.22장을 완료했고, 상한 4에서는 60장을 완료했습니다. 미완료 비율은 16.17에서 0퍼센트로, 지연 p95는 74.42에서 22.75밀리초로 줄었습니다. 다만 객체가 없는 프레임의 반복 시험이고 GUI와 짐벌은 포함하지 않습니다. 실카메라 수신은 별도 시험에서 약 18에서 22프레임 수준이었으므로, 이 숫자로 전체 시스템 60fps나 실카메라 30fps를 주장하지 않습니다.

[전환] 그 결과를 화면에서 끝내지 않고, 짐벌 명령으로 연결합니다.

10. 표적과 화면 중심의 차이를, 움직임으로

C++ 브리지는 기존 Runtime의 제어기와 장치 실행 경계를 재사용하며 방향과 공통 속도 명령을 계산합니다. 불감대와 속도 제한을 적용하고 수동 입력, 관측 상실, 오래된 입력도 처리합니다. 공개 실행 스크립트는 적분항이 0인 PD 동작입니다. 실제 카메라와 짐벌에 가상 표적을 주는 시험에서는 정지 후 상하 반전이 네 번에서 한 번으로 줄었습니다. 하지만 별도 가로 시험의 뒤처짐은 14.3에서 18.6픽셀로 늘었습니다. 조건별 한 번의 결과이므로 전체 추종 성능이 개선됐다고 일반화하지 않습니다. 최종 옥상 시험에서는 실제 선택 모델과 제어 설정을 고정해 운용 동작을 확인해야 합니다.

11. 선택하고, 확인하고, 바로 멈춘다

사용자는 이 화면에서 표적을 고르고 시스템 상태를 확인합니다. 현재 화면은 저장소에서 제공한 합성 미리보기입니다. 실제 현장 성능을 보여주는 장면은 아니고, 기능과 배치를 설명하기 위해 넣었습니다. 먼저 영상의 사람을 선택하면 선택 ID가 제어 쪽으로 전달됩니다. 운용자는 현재 표적과 연결 상태를 보면서 자동 추종을 사용할 수 있고, 필요할 때 방향키나 터치로 수동 개입할 수 있습니다. 정지도 같은 화면에서 바로 할 수 있어야 합니다. 검출과 추적을 구현해도 사용자가 무엇을 선택했는지, 현재 연결과 추종 상태가 어떤지 알 수 없으면 운용하기 어렵습니다. 그래서 이 화면은 영상을 보여주는 창이면서 동시에 제어와 확인의 접점입니다. 실제 운용 GUI 캡처를 받으면 이 미리보기 한 장을 교체하고, 최종 영상 전송 모드와 상태 표시가 데모 설정에 맞는지도 확인하겠습니다.

[전환] 이제 전체 동작을 하나의 장면으로 확인하는 순서입니다.

진행 메모: 합성 미리보기라고 먼저 말합니다. 기능 설명에만 사용하고 화면에 보이는 FPS·지연은 읽지 않습니다. 실제 운용 캡처가 오면 이 한 장을 교체합니다.

13. 구현한 것에서, 현장에서 쓸 수 있는 것으로

지금까지는 각 단계에서 확보한 근거를 설명드렸습니다. 검출 모델을 보드에서 실행했고, 같은 검출을 사용한 비교에서 ID 연결이 개선됐으며, GUI와 제어 브리지를 장치 명령으로 연결했습니다. 다만 이 결과를 합쳐서 현장 성능이 모두 검증됐다고 말할 수는 없습니다. 최종 운용 모델과 제어 설정을 고정한 다음, 거리별로 사람이 검출되는지, 가림 뒤에도 선택한 ID를 유지하는지, 실제 움직이는 사람을 짐벌이 따라가는지 확인해야 합니다. 시간도 구분해 보겠습니다. 30Hz는 입력 주기가 약 33.3밀리초라는 뜻입니다. 처리량이 그 속도를 따라가는지와 같은 프레임이 결과로 나오기까지 걸린 시간은 따로 계측해야 합니다. 아직 수치가 확정되지 않은 거리와 유지 기준은 현장 시험 전에 고정하고 같은 조건으로 비교하겠습니다.

14. 찾고, 이어가고, 따라가는 시스템

발표를 세 가지 동작으로 정리하겠습니다. 첫째, 열화상에서 사람을 찾기 위해 학습과 검증, 보드 배포를 연결했습니다. 둘째, 사람을 한 프레임씩 찾는 데서 그치지 않고 가림과 방향 변화 뒤에도 같은 ID로 이어가도록 추적기를 비교하고 조정했습니다. 셋째, 그 위치를 사용자 선택과 짐벌 제어, 운용 화면으로 연결했습니다. 이 과정에서 모델 정확도와 속도, ID 유지와 누락, 부드러운 제어와 뒤처짐 사이의 절충을 확인했습니다. 각 실험의 좋은 숫자만 합치는 대신, 실제 운용 설정에서 하나의 동작으로 검증하는 것이 마지막 과제입니다. 현장 검증에서는 검출부터 정지까지 같은 조건을 유지하고 판단하겠습니다. 이상 5팀 올빼미였습니다. 감사합니다.
