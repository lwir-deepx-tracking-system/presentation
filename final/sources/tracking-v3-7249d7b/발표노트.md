# 추적 알고리즘 발표 노트 (정하건)

슬라이드 5장, 약 3분 30초 기준. 쪽 번호는 최종 취합 때 바뀔 수 있습니다.

## 01 추적 알고리즘: 세 가지 구현과 GUI 선택 (40초)
- 추적은 프레임마다 같은 사람에게 같은 번호(Track ID)를 붙이는 일입니다. 운용자가 고르는 것이 이 ID라서, ID가 바뀌면 짐벌이 표적을 잃습니다.
- ByteTrack, OC-SORT, BoT-SORT 세 가지를 모두 C++로 구현했고, 운용 중에 GUI에서 골라 쓸 수 있게 했습니다.
- 같은 검출로 비교하면 BoT-SORT가 종합 점수(HOTA 60.7)가 가장 높았고, ID 전환은 ByteTrack 최선 2,964회에서 566회로 줄었습니다.

## 02 세 알고리즘의 구조 차이 (40초)
- ByteTrack은 검출을 점수로 나눠 두 번 매칭하고, 움직임은 Kalman 예측에만 기댑니다.
- OC-SORT는 실제 관측을 중심에 둡니다. 이동 방향(OCM)을 매칭에 더하고, 놓친 Track은 마지막 관측 위치로 다시 찾고(OCR), 다시 찾으면 놓친 구간의 상태를 다시 계산합니다(ORU).
- BoT-SORT는 ByteTrack 흐름을 따르되, 폭과 높이를 따로 추정하고 매칭 비용에 검출 점수를 반영합니다. 원래는 외형 비교(ReID)도 쓰지만 이번 비교에서는 껐습니다.
- OC-SORT는 공식 구현과, BoT-SORT는 팀 추적 서버의 Python 구현과 출력이 같은 것을 확인했습니다.

## 03 GUI에서 추적기를 바꾸는 구조 (35초)
- PC GUI에서 번호를 고르면 TCP로 변경 요청이 오고, 런타임이 카탈로그에서 그 번호의 설정 파일을 찾아 새 추적기를 만듭니다.
- 교체는 추적을 멈추지 않고 다음 프레임 경계에서 일어나고, 만들기에 실패하면 쓰던 추적기를 그대로 씁니다. GUI는 접수와 완료 두 번의 응답으로 결과를 확인합니다.
- 알고리즘을 더 넣을 때도 yaml 파일과 카탈로그 한 줄만 늘리면 됩니다.

## 04 성능 비교 (50초)
- 각 알고리즘의 최종 설정으로 비교하면, BoT-SORT가 HOTA 60.7, IDF1 67.5%, MOTA 74.7%, 정밀도 89.5%로 가장 좋았습니다.
- 낮은 점수 검출도 이어 붙이도록 매칭 기준을 넓혀 ID 전환을 줄였고, 새 ID는 점수 0.5 이상 검출로만 만들어 헛 ID를 막았습니다.
- 다만 ID 전환 수 자체는 OC-SORT가 531회로 가장 적고 재현율도 높습니다. 가려졌다 나타나는 사람을 마지막 위치로 다시 잇는 구조 덕분입니다. 그래서 세 가지를 모두 남겨 장면에 따라 GUI에서 바꿔 쓸 수 있게 했습니다.

## 05 BoT-SORT 파라미터 조정과 최종 설정 (45초)
- 한 번에 하나씩 바꿔 본 뒤 좋은 값을 조합했습니다.
- 새 ID 기준을 0.25에서 0.5로 올리자 ID 전환이 1,001회에서 723회로, 매칭 기준을 0.9로 넓히자 575회로, 막 생긴 Track을 엄격하게 잇자 566회로 줄었습니다.
- 새 ID 기준 0.6은 사람을 더 놓쳤고, 매칭 기준 0.92·0.95와 막 생긴 Track 기준 0.8은 오히려 나빠서 제외했습니다.
- 결론: 기본 추천은 BoT-SORT, 가림이 잦은 장면은 OC-SORT입니다.
