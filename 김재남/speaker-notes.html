슬라이드로 돌아가기

슬라이드 05 · 전체 시스템 구성

약 1분 20초 분량의 원고다. 전체 담당 슬라이드의 목표 시간은 총 4분 30초다.

0:00–0:20 · 전체 흐름

전체 시스템은 열화상 카메라, Orange Pi, DEEPX NPU, 2축 짐벌, 그리고 PC로 구성됩니다. 카메라에서 얻은 열화상을 보드에서 처리하고, PC에서 사용자가 선택한 표적을 따라 카메라 방향을 조정하는 흐름입니다. 그림의 실선은 장치 간 데이터와 명령 연결이고, 점선은 짐벌이 카메라 방향을 바꾸는 관계입니다.

0:20–0:45 · 보드와 NPU의 역할

카메라는 USB를 통해 16-bit 열화상 원본을 Orange Pi에 전달합니다. Orange Pi는 영상을 모델 입력으로 전처리하고, PCIe로 연결된 NPU에 객체 검출 추론을 요청합니다. 추론 결과는 보드에서 후처리와 추적을 거쳐 객체의 위치와 ID로 연결됩니다. 이렇게 보드가 전체 처리 흐름을 관리하고 NPU가 모델 추론을 수행하도록 역할을 나눴습니다.

0:45–1:05 · PC와의 연결

PC와 보드는 Ethernet으로 연결됩니다. 보드는 영상과 객체 메타데이터를 보내고, PC는 이를 표시하면서 사용자가 선택한 표적 ID와 운용 모드를 보드로 전달합니다. 영상 표시와 운용 입력을 PC에서 수행하고, 그 선택을 적용하는 처리와 제어는 보드에서 이어집니다.

1:05–1:20 · 짐벌 구동

보드는 선택한 표적의 위치를 바탕으로 짐벌에 Serial 명령을 전달합니다. 짐벌이 카메라 방향을 바꾸면 바뀐 장면이 다시 입력됩니다. 이 연결 위에서 검출, 추적, 표적 선택과 방향 제어가 반복됩니다.

발표자 참고

- 이 구성도는 장비 역할과 연결을 요약한다. 실제 장치 사진이나 실물 통합 시험의 측정 결과는 아니다.

- camera.cpp와 I3System.cmake의 USB 카메라 연결, DEEPX NPU의 PCIe 연결, /dev/ttyUSB0 기반 Serial 제어, network_setup.md의 Ethernet 연결을 근거로 표시했다.

- 영상은 UDP 5000, 메타데이터는 UDP 5001, 명령 경로는 TCP 5002를 사용한다. 발표 본문에서는 포트 번호를 생략했다.

- 점선은 카메라 방향의 물리적 변화를 나타낸다. 짐벌의 정밀 각도 피드백이나 제어 성능을 검증했다는 의미는 아니다.

- NPU 모델 로딩·추론·텐서 검증 및 실물 폐루프 성능은 이번 슬라이드 제작에서 미검증이다.

슬라이드 08 · 열화상 전처리와 후처리

약 1분 10초 분량이다. 도식의 640×480 → 640×640은 기본 모델 설정의 예시다.

0:00–0:20 · 입력 변환

카메라 입력은 640×480의 16-bit 단일 채널 열화상입니다. 전처리에서는 입력 형식과 크기를 확인하고, 설정한 값의 범위를 0부터 255까지의 8-bit 값으로 변환합니다. 이어서 같은 회색 값을 세 채널로 복제해 모델이 요구하는 입력 형식에 맞춥니다.

0:20–0:40 · Letterbox

기본 모델 입력은 640×640입니다. 원본을 정사각형으로 늘리면 객체 비율이 달라지므로, 종횡비를 유지하는 letterbox를 사용합니다. 이 예시에서는 영상 크기는 유지하고 위와 아래에 80픽셀씩 여백을 추가합니다. 적용한 배율과 여백은 후처리에서 사용할 수 있도록 함께 기록합니다.

0:40–1:10 · 후처리와 원본 좌표 복원

모델 출력은 confidence 기준으로 걸러내고, 설정에 따라 NMS로 중복 박스를 정리합니다. 이후 모델 좌표에서 padding을 빼고 배율로 나누어 원본 영상 좌표로 복원합니다. 박스가 영상 밖으로 나가면 원본 범위로 제한합니다. 이 좌표를 추적과 GUI 표시에서 공통으로 사용합니다. 전처리 조건은 모델 설정으로 관리하며, 학습과 export에서 사용한 조건에 맞춰야 합니다.

발표자 참고

- 현재 LwirPreprocessor는 16→8-bit 변환 후, 공간 변환과 채널 복제를 선택한 경로에서 수행한다. 도식은 논리 기능 순서다.

- 모델 입력이 카메라와 같은 크기면 resize와 padding을 생략한다. 기본 640×640 모델은 resize 없이 padding만 수행한다. 실제 배율 변경이 필요할 때 resize한다.

- 기본 YAML의 clip 범위는 0..65535, pad_value는 114다. 실제 학습 일치 여부와 성능 검증은 모델별로 확인해야 한다.

- NMS 적용 여부와 class-agnostic 여부는 설정에 따른다. 모든 export 모델에서 반드시 NMS를 수행한다고 확대하지 않는다.

- letterbox 배율은 min(모델 너비/원본 너비, 모델 높이/원본 높이)다. 좌표는 padding 제거 후 scale 역변환하며 원본 경계로 clamp한다.

- 도식은 처리 방식의 개념도다. 실제 NPU 추론 출력이나 검출 성능 측정 결과가 아니다.

슬라이드 11 · 파이프라인과 큐 정책

약 1분 분량의 원고다. 실제 낭독 속도로 최종 조정한다.

0:00–0:20 · 단계별 대기 분리

카메라 수신, 탐지, 추적, 제어와 GUI 송신을 독립 thread로 구성하고 queue로 연결했습니다. 각 단계의 처리 속도와 대기 원인이 다르기 때문에, 단계별 작업을 겹쳐 수행할 수 있도록 구성했습니다. 원본 프레임은 추적 결과와 함께 공유해 GUI에서 대응하는 영상을 사용할 수 있습니다.

0:20–0:45 · 경로별 큐 정책

큐에 오래된 프레임이 계속 쌓이면 현재 장면과 출력 사이의 시차가 커질 수 있습니다. 그래서 카메라에서 탐지로 가는 큐와 GUI 큐는 최신 두 개, 제어 큐는 최신 한 개를 유지합니다. 한도를 넘으면 오래된 항목을 제거합니다. 탐지 결과는 비동기로 완료되더라도 제출 순서를 복원한 뒤 FIFO로 추적 단계에 전달합니다.

0:45–1:00 · 설계 절충

이처럼 모든 경로에 같은 정책을 적용하지 않고, 추적에는 순서를, 제어와 화면 출력에는 최신성을 우선했습니다. 프레임 일부를 버리는 대신 오래된 결과의 누적을 줄이도록 설계한 것입니다.

발표자 참고

- 개수는 큐에 대기 중인 항목 기준이다. 이미 처리 중인 프레임은 별도다.

- 탐지 결과 큐는 현재 일반 FIFO이며 용량 제한이 없다. 전체 파이프라인의 메모리나 지연 상한을 보장한다고 설명하지 않는다.

- 원본 프레임 공유는 shared_ptr<const FrameContext>로 수명을 전달한다는 의미다. 모든 영상 변환이 zero-copy라는 의미는 아니다.

- 이 슬라이드는 코드의 구조와 정책을 설명한다. FPS·CPU 사용률·지연 감소율의 실측 수치는 포함하지 않았다.

슬라이드 12 · PC 애플리케이션과 통신

약 1분 분량이다. 런타임 송수신 구현과 PC 통신 계약을 기준으로 설명한다.

0:00–0:20 · GUI와 채널 역할

PC는 영상과 객체 박스, ID를 표시하고 사용자가 표적과 운용 모드를 선택하는 역할입니다. 보드와 PC 사이에서는 영상, 메타데이터, 명령의 세 경로를 구분했습니다. 영상은 RTP와 UDP 5000으로, 객체 정보는 UDP 5001로 보내고, 명령과 상태는 TCP 5002로 주고받습니다.

0:20–0:40 · 영상과 메타데이터 대응

영상과 메타데이터는 서로 다른 채널로 도착하므로 같은 프레임인지 식별할 기준이 필요합니다. 송신부는 영상의 RTP timestamp에 대응하는 값을 메타데이터에도 기록합니다. 원본 frame ID와 객체 정보도 함께 보내, PC가 대응하는 영상 위에 박스와 ID를 표시할 수 있도록 구성했습니다.

0:40–1:00 · 명령과 상태

표적 선택과 AUTO, MANUAL 전환 같은 명령은 TCP로 전달합니다. 보드는 ACK로 명령의 처리 결과를 응답하고, STATUS로 현재 모드와 표적, 짐벌 상태를 전달합니다. 이를 통해 명령을 보냈다는 사실과 실제 운용 상태를 구분해서 확인하도록 구성했습니다.

발표자 참고

- 현재 로컬 검토 범위는 Runtime의 GuiSender, PcGuiProtocol, TrackingCommandHandler다. PC 앱 소스·실제 GUI 화면과 동기화 표시 동작은 이번 제작에서 직접 검증하지 않았다. 도식은 역할과 통신 계약을 표현한다.

- 영상·메타데이터 대응 키는 동일한 90kHz RTP timestamp다. 메타데이터의 frame_id는 원본 캡처 ID다. 두 값이 같은 숫자라는 의미는 아니다.

- UDP의 도착 순서·누락·재정렬이 자동 해결된다는 뜻은 아니다. 실제 PC 수신부는 timestamp를 기준으로 대응시키는 처리가 필요하다.

- STATUS는 연결 시와 상태 변화에 따라 제공된다. 주기적 강제 송신이나 모든 명령의 실행 완료를 보장한다고 설명하지 않는다.

- tracking handler에서 AUTO 표적 선택과 MANUAL, 수동 MOVE를 처리한다. MOVE는 프로토콜상 별도 ACK가 없고 HOME은 NOT_READY다. 본문 ACK 설명은 응답이 정의된 명령에 해당한다.

- Pipeline 카테고리의 모델·트래커 변경은 별도 확장이다. 해당 확장을 현재 PC GUI가 구현했다고 가정하지 않았다.

- 네트워크 전달 지연이나 영상·메타데이터 동기화의 실측 성능은 이 슬라이드에서 주장하지 않는다.
