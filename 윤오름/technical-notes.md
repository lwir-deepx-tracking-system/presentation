# 윤오름 담당 발표 초안

조사일: 2026-11-16. GitHub 공개 변경 기록·기본 브랜치 파일과 Notion 작업 기록을 대조한 내용 초안이다. 발표 담당 확정표가 아니며 실제 개발·설계·통합 기여에서 발표 범위를 도출했다. 이번 조사에서 빌드·보드 시험은 수행하지 않았다.

## 담당 범위 판단

- 중심: 10 표적 선택과 짐벌 제어, 12 PC 애플리케이션과 통신.
- 함께 초안 작성: 4 요구사항과 설계 기준, 5 전체 시스템 구성, 13 시험 및 성능 결과.
- 공동 설명 범위: 11 실시간 처리와 영상 송신. PC 연동·송수신 정합·계측은 다룰 수 있으나 Runtime 파이프라인 전체나 인코더 구현을 단독 기여로 표현하지 않는다. 영상 변경 PR #7 작성자는 seu20이고, 이후 통신 정합 PR #9와 통합 PR #10 작성자는 x-orme다. 통합 PR 작성자와 포함된 모든 코드의 원저자는 같다고 볼 수 없다.
- 기존 1·3번은 디자인 예시다. 예시 제작을 발표 담당 배정으로 해석하지 않는다.
- 6·7·8·9번의 모델·양자화·전후처리·추적 알고리즘 상세는 해당 개발자의 근거를 반영한다.

## 01. 표지 — 20초

기존 index.html의 표지를 통합했다. 프로젝트명·팀원·멘토와 운용 개념도를 유지한다.

발표 노트: “안녕하십니까. DEEPX NPU를 이용한 LWIR 표적 추적 시스템 구현을 발표할 5팀 올빼미입니다. 열영상으로 객체를 검출하고, 선택한 표적을 추적해 2축 짐벌 제어로 연결한 시스템을 소개하겠습니다.”


## 02. 팀 소개 — 1분

화면 구성: 누끼 인물 사진 5장을 가로로 배치하고, 이름·주요 역할·세부 담당 업무를 표시한다. 팀장과 멘토를 함께 소개한다.

| 팀원 | 주요 역할 | 세부 담당 |
| --- | --- | --- |
| 윤오름 | PM·시스템 통합 | PC GUI·통신, 짐벌 제어·통합 시험 |
| 김재남 | Runtime 개발 | 실시간 처리 파이프라인, 모델·트래커 관리 |
| 윤관 | AI 검출 모델 | 검출 모델 선정·학습, 데이터·정확도 평가 |
| 정하건 | 객체 추적 | 추적 알고리즘·옵션 개선, 추적 성능 평가 |
| 홍정호 | NPU 최적화 | 모델 경량화·양자화, NPU 배포 |

발표 노트: “저희는 5팀 올빼미입니다. 저는 팀장 윤오름으로 시스템 통합과 PC 애플리케이션, 짐벌 제어를 담당했습니다. 김재남 팀원은 Runtime 파이프라인과 모델·트래커 관리를, 윤관 팀원은 검출 모델 학습과 평가를 담당했습니다. 정하건 팀원은 객체 추적 알고리즘 개선과 성능 평가를, 홍정호 팀원은 NPU 최적화와 양자화·배포를 담당했습니다. 천준호 선임연구원님의 멘토링 아래 시스템을 개발했습니다.”

역할 표기는 초기 직책보다 최근 실제 작업 내용을 우선해 요약했다. 홍정호 세부 항목은 팀 역할 기록과 발표 목차의 담당 영역을 설명하며 완료 성과를 증명하는 문구가 아니다. 팀명 유래는 확인된 문구가 없어 임의로 작성하지 않았다.

사진 원본: reference/human/윤오름.png, 김재남.png, 윤관.png, 정하건.png. 원본은 수정하지 않고 담당 폴더의 assets/team/에 복사했다. 홍정호.png는 사용자 지시에 따라 윤오름 사진의 임시 복사본이다. 수령 후 assets/team/홍정호.png를 실제 누끼 사진으로 교체하고 HTML의 임시 표시·대체텍스트·출처 문구를 갱신한 뒤 PDF를 다시 출력한다.

## 03. 프로젝트 목표와 운용 시나리오 — 1분

기존 index.html의 운용 시나리오를 통합했다. 열화상 객체 검출 → 표적 선택 → 추적·짐벌 제어와 영상 피드백 흐름을 유지한다.

발표 노트: “운용은 세 단계입니다. 열영상에서 객체를 검출하고, 사용자가 PC에서 추적할 표적을 선택합니다. 시스템은 선택 객체의 ID를 따라가며 영상 중심과의 오차로 짐벌을 제어합니다. 짐벌 회전으로 바뀐 영상을 다시 받아 같은 과정을 반복합니다.”

도식은 운용 개념이며 실제 장치 사진이나 측정 결과가 아니다.


## 04. 시스템 요구사항 — 1분 20초

핵심 문장: **열영상 입력부터 표적 추종·상태 확인까지, 시스템이 충족해야 할 기준을 정의한다.**

| 구분 | 요구사항 | 목표·확인 기준 |
| --- | --- | --- |
| R1 실시간 처리 | 30Hz 입력 영상의 한 프레임 처리를 약 33.3ms 이내에 완료해야 한다. | 프레임 처리시간 ≤ 33.3ms |
| R2 객체 검출 | 지정된 거리 범위 안에서 대상 객체를 검출할 수 있어야 한다. | 최소·최대 검출 거리 [기준 확정 필요] m |
| R3 객체 추적 | 동일 객체의 ID를 유지하며 정해진 기준 이상으로 추적을 유지해야 한다. | 최소 유지 시간·유지율 [기준 확정 필요] |
| R4 짐벌 추종 | 사용자가 추적 명령을 내린 객체를 2축 짐벌 제어로 추종해야 한다. | 선택 표적의 Pan·Tilt 추종 |
| R5 PC 운용 | PC GUI에서 영상·추적 결과·현재 시스템 상태를 확인할 수 있어야 한다. | 영상·표적·운용 상태 표시 |

화면 구성: 구분·요구사항·목표 기준을 담은 5행 표. 구현 방법은 이후 기술 슬라이드에서 설명한다.

발표 노트: “시스템 요구사항은 다섯 가지입니다. 첫째, 30Hz 입력에 맞춰 한 프레임 처리를 약 33.3ms 이내에 완료하는 것을 목표로 합니다. 둘째, 지정 거리 범위에서 객체를 검출해야 합니다. 셋째, 같은 객체의 ID를 유지하며 정해진 기준 이상으로 추적해야 합니다. 넷째, 사용자가 선택한 표적을 2축 짐벌로 추종해야 합니다. 마지막으로, PC GUI에서 영상과 추적 결과, 운용 상태를 확인할 수 있어야 합니다.”

기준: 2026-11-16 사용자 설명. 수치는 달성 결과가 아닌 목표다. 검출 거리, 추적 시간·유지율은 임의로 확정하지 않았다. 검출 시험의 객체 종류·판정 지표·환경 조건과 추적 유지율의 분모·ID 변경 처리·가림 조건을 확정해야 한다. 33.3ms의 처리 시작·종료 지점과 평균·최대 등 판정 통계도 시험 전에 확정한다. 병렬 파이프라인의 처리량과 개별 프레임 지연은 구분하여 검증한다.

## 05. 전체 시스템 구성 — 1분 20초

핵심 문장: **보드가 검출·추적·구동을 수행하고, PC가 표적 선택과 운용 상태 확인을 담당한다.**

화면 문구:

- LWIR 카메라: 열영상 입력
- Orange Pi + DEEPX NPU: 검출·추적과 제어 계산
- 짐벌: 보드의 Serial 명령으로 구동
- PC: 영상·Track 표시, 표적 선택, 수동 조작, 모델 전환 요청

도식: Camera → Orange Pi/NPU → Control → Gimbal. 보드–PC 사이에 영상 UDP 5000, 메타데이터 UDP 5001, 명령·상태 TCP 5002를 구분한다. 영상·메타데이터는 보드→PC, TCP는 양방향이다.

발표 노트: “PC는 사용자의 운용 의도를 보드에 전달합니다. 보드는 현재 표적과 장치 상태를 검증하고 실행하며, 상태를 다시 PC에 알립니다. 영상 수신과 제어 연결은 별도로 관리합니다.”

근거: [Runtime 통신 정합 PR #9](https://github.com/lwir-deepx-tracking-system/runtime/pull/9), [PC 통합 PR #3](https://github.com/lwir-deepx-tracking-system/pc-application/pull/3).

## 10. 표적 선택과 짐벌 제어 — 1분 10초

핵심 문장: **선택한 표적의 중심 오차를 줄이고, 입력 상실이나 수동 개입에는 이동을 정지한다.**

화면 문구:

- 선택 ID의 BBox 중심과 영상 중심의 오차 계산
- P 제어를 기본으로 공통 SPD와 축별 방향 결정
- Deadband·속도 상한·변화율 제한 적용
- 표적 상실·오래된 입력·연결 종료 시 STOP, 재획득·모드 전환 처리

도식: BBox 중심과 화면 중심 사이 오차 화살표 → 제어 계산 → 방향·SPD → 짐벌. 아래에 AUTO → 표적 상실/정지 대기 → 동일 표적 재획득 또는 MANUAL 흐름을 배치한다.

발표 노트: “표적의 위치 오차로 방향과 속도를 결정합니다. 중앙 부근에서는 Deadband로 정지시키고, 급격한 속도 변경을 제한합니다. 자동 계산과 수동 명령은 하나의 장치 실행 경로에서 처리해 모드가 바뀐 뒤 이전 자동 명령이 실행되는 문제를 방지합니다.”

초안 주의: PID 선택 기능과 최종 운용 제어기는 구분한다. 실기 튜닝 PR은 P 제어를 유지한다. SPD를 각속도 실측값으로 표현하지 않는다. HOME은 현재 STOP 후 NOT_READY이며 원점 이동 완료 기능으로 소개하지 않는다. 정량 추종 오차·최종 안정성·물리 STOP 시간은 [측정 예정].

근거: [제어 설계](https://app.notion.com/p/40d9de3f14a28051b1d3d992e8ec1f1e), [현재 AUTO 구현 문서](https://github.com/lwir-deepx-tracking-system/runtime/blob/main/docs/auto_control.md), [실기 튜닝 PR #14](https://github.com/lwir-deepx-tracking-system/runtime/pull/14).

## 11. 실시간 처리와 영상 송신 — 1분 50초 / 공동 내용

핵심 문장: **처리 단계와 송신을 분리하고, 최신 프레임을 전달하면서 영상과 Track의 대응을 유지한다.**

화면 문구:

- Camera → Detection → Tracking → GUI / Control 분기
- 제한된 큐와 최신 결과 유지
- 동일 원본 프레임·Track 결과 전달
- JPEG/H.264 송신과 PC 수신 설정 정합

도식: worker·queue 흐름과 GUI/Control 분기를 중심에 놓고, 인코더 비교표는 실제 결과를 확보한 뒤 오른쪽에 배치한다.

비교표 자리: 동일 입력·실행 환경·코덱 설정에서 CPU 사용률 [측정 예정], 표시 FPS [측정 예정], Encode+RTP [측정 예정], 수신량 [측정 예정]. 현재 코드가 코덱 두 종류를 지원한다는 사실과 우열을 실측했다는 주장은 구분한다.

발표 노트: “추적 결과에 대응하는 원본 영상을 함께 전달하고, PC에서는 RTP timestamp로 영상과 박스를 대응시킵니다. 큐를 무한히 늘리는 대신 최신성을 유지합니다. 인코더 선택은 동일한 입력과 보드 조건의 측정 결과로 설명하겠습니다.”

분담 경계: worker·비동기 추론·큐 내부 설계는 담당자 설명을 반영한다. 이 초안의 중심은 송수신 정합·동기화·측정 해석이다.

근거: [영상 송신 PR #7](https://github.com/lwir-deepx-tracking-system/runtime/pull/7), [통신 정합 PR #9](https://github.com/lwir-deepx-tracking-system/runtime/pull/9), [Runtime 통합 PR #10](https://github.com/lwir-deepx-tracking-system/runtime/pull/10).

## 12. PC 애플리케이션과 통신 — 1분

핵심 문장: **영상·검출 결과를 대응시키고, 사용자의 명령과 보드의 실제 상태를 연결했다.**

화면 문구:

- 영상과 BBox: RTP timestamp 기반 대응
- 표적 선택·AUTO/MANUAL·방향키 수동 조작
- 모델 교체: 접수와 완료 응답 구분
- 보드 STATUS 기반 상태 표시·재접속 처리

도식: 최신 실제 GUI 화면을 크게 배치하고 영상·타깃 제어·모델 선택·상태 표시 네 곳만 표시한다. GUI 이미지 [확인 필요: 최신 실행 화면 확보]. 바이트 필드 표는 발표 본문보다 보충자료에 둔다.

발표 노트: “영상과 메타데이터는 독립적으로 도착하므로 RTP timestamp가 맞는 박스만 적용합니다. 사용자의 클릭이나 명령 전송만으로 성공 상태를 표시하지 않고, 보드가 알려준 상태와 모델 교체 완료 응답을 기준으로 화면을 갱신합니다.”

근거: [PC 통합 PR #3](https://github.com/lwir-deepx-tracking-system/pc-application/pull/3), [현재 PC 문서](https://github.com/lwir-deepx-tracking-system/pc-application/blob/main/README.md).

| Runtime 통계 수신 | PC PR #5의 합성 fixture·중복 제거·세대 초기화·CSV 검증 | PC 통계 수신·기록 구현 확인 |
| 실물 추종 튜닝 | PR #14의 실기 진동 관찰과 설정 조정 | 실기 튜닝 수행, 최종 정량 안정성은 미확인 |
| 성능 비교 | 원본 로그와 시험 조건 [확인 필요] | FPS·CPU·추종 오차·정지 시간 [측정 예정] |

발표 노트: “모의 송신기로 패킷과 상태 처리를 확인한 뒤, 보드 통합과 실제 장치 튜닝으로 검증 범위를 넓혔습니다. PC 수신에서 그리기까지의 시간과 보드 내부 처리시간은 구분하며, 통계 원본을 남겨 모델이나 조건별 비교가 가능하도록 했습니다.”

계측 주의: PC 수신→paint는 전체 카메라→화면 지연이 아니다. Runtime 성능 확장의 PC 수신 구현은 확인됐지만 보드 송신 연동·실측 완료로 확대하지 않는다. 현재 숫자를 얻기 위한 로그 수집과 실기 시험은 이번 초안 작업에서 수행하지 않았다.
