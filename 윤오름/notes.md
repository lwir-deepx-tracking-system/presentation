# 윤오름 담당 발표 노트

2026-11-18 개정. 정하건 v3(7249d7b)를 팀원 제공 근거로 반영했다. 장치·Runtime·GUI 재시험은 하지 않았다.

## 설명 범위

- 중심: 전체 시스템 및 PC 통신·표시·계측, 표적 선택과 짐벌 제어, 추적기 변경 요청·상태 확인.
- 정하건 파트: 세 추적기의 내부 구조·튜닝·성능 비교. 본 자료에서 알고리즘 개발을 윤오름 단독 기여로 설명하지 않는다.
- 김재남·홍정호 파트: Runtime 파이프라인·멀티스레드·NPU 가속·최적화. PC 송수신·계측 경계와 구분한다.
- 웹 GUI·HTTP·Picture First·브라우저 단축키는 발표 본문에서 제외했다. 실제 운용 앱 캡처·설정은 최종 반영한다.
- 팀원 자료를 믿고 통합하되, 문서 편집이 새 장치 검증을 의미하지는 않는다.

## 01. 프로젝트 소개
전체 목차 담당 주제: 01 / 목표 20초

안녕하십니까. DEEPX NPU를 이용한 LWIR 표적 추적 시스템 구현을 발표할 5팀 올빼미입니다. 윤오름, 김재남, 윤관, 정하건, 홍정호 다섯 명이 천준호 선임연구원님의 멘토링 아래 개발했습니다. 먼저 팀원 역할을 소개하겠습니다.

화면 진행: 프로젝트 제목 → 팀명·팀원 → 멘토

## 02. 팀 구성 및 역할
전체 목차 담당 주제: 02 / 목표 35초

저희는 5팀 올빼미입니다. 팀장인 저는 시스템 설계와 통신, GUI와 짐벌 제어를 맡았습니다. 김재남 팀원은 Runtime과 멀티스레드 파이프라인 구현, 윤관 팀원은 적외선 모델 학습과 경량화를 맡았습니다. 정하건 팀원은 추적 알고리즘 검증과 개선, 홍정호 팀원은 Runtime 최적화와 NPU 처리 가속을 맡았습니다.

화면 진행: 사진 순서대로 소개 → 주요 담당·핵심 기여 → 팀원 역할 상세는 문서

## 03. 프로젝트 소개
전체 목차 담당 주제: 03 / 목표 30초

저희 프로젝트는 열영상에서 사람을 검출하고, 사용자가 고른 사람을 카메라가 따라가도록 하는 시스템입니다. LWIR은 장파적외선 열영상이고, DEEPX NPU는 보드에서 검출 모델을 실행하는 가속기입니다. 카메라 영상에서 사람과 ID를 구한 뒤, PC에서 추적할 대상을 고르면 그 위치를 좌우·상하 짐벌 제어로 연결합니다. 이 네 단계가 하나로 이어지는 것이 프로젝트의 목표입니다.

화면 진행: 무엇을 만드는가 → LWIR·NPU의 의미 → 영상→검출·ID→선택→추종

## 04. 시스템 요구사항
전체 목차 담당 주제: 04 / 목표 45초

저희가 잡은 요구사항은 네 가지입니다. 시간 측면에서는 30헤르츠 입력을 따라가는 것을 목표로 했습니다. 입력 주기로는 약 33.3밀리초입니다. 검출은 정한 거리 범위에서 사람이 잡혀야 하고, 추적은 가림 뒤에도 선택한 ID가 이어져야 합니다. 마지막으로 짐벌 두 축이 그 표적을 따라가고 PC에서 상태를 확인하고 정지할 수 있어야 합니다. 거리와 ID 유지의 수치 기준은 최종 시험 전에 확정해야 하는 항목으로 남겨뒀습니다.

화면 진행: 30Hz → 거리·ID 기준 → 추종·상태·정지

## 05. 시스템 구성
전체 목차 담당 주제: 05 / 목표 35초

윗줄을 따라가면 전체 동작이 보입니다. 카메라에서 보드로 영상이 들어오고, 보드가 사람과 ID를 구합니다. 선택한 표적의 위치가 짐벌로 전달되면 카메라 방향이 바뀝니다. 바뀐 영상이 다시 입력됩니다. PC GUI는 이 반복 동작을 보면서 표적 선택과 수동 조작을 전달합니다. 최신 추적 자료에 따라 ByteTrack, OC-SORT, BoT-SORT 세 가지를 GUI에서 선택하는 구조를 반영했습니다.

화면 진행: 입력→판단→구동 → 다음 영상 → 운용자 개입

## 06. 표적 선택 및 짐벌 제어
전체 목차 담당 주제: 10 / 목표 65초

사용자가 선택한 Track ID의 최신 위치에서 조준점을 정하고 화면 목표점과의 오차를 계산합니다. 이 오차가 두 축 제어의 입력입니다. 제어기에서는 불감대와 속도 제한을 적용해 짐벌 명령으로 연결합니다. 추적기 선택과 추적 대상 ID 선택은 별개입니다. 추적기 교체 뒤 선택 ID를 어떻게 처리할지는 최종 운용 설정과 맞춥니다. 공개된 다른 실행 스크립트의 제어값이나 단축키를 현재 장치 설정으로 옮겨 설명하지 않습니다.

화면 진행: 조준점 → 화면 목표점 → 두 축 오차

## 07. 영상·메타데이터 통신
전체 목차 담당 주제: 11 / 목표 65초

제 담당은 Runtime의 전체 파이프라인 구현보다 PC와 보드 사이의 통신 경계입니다. PC 앱은 RTP/UDP 영상과 UDP 메타데이터를 수신하고 영상과 사람 상자를 대응해 표시합니다. JPEG와 H.264 수신 및 FPS, 지연, 연결 상태의 계측 기능을 구현했습니다. 명령과 상태 확인은 TCP 경로로 분리합니다. 파이프라인과 추적기 내부 구현은 각 담당자의 설명으로 이어가고, 여기서는 PC 수신과 표시, 제어 요청의 연결을 설명합니다.

화면 진행: 영상·메타데이터 → 같은 프레임 대응 → 제어·계측 경계

## 08. 추적기 선택 및 변경 확인
전체 목차 담당 주제: 12 / 목표 70초

정하건 팀원의 최신 자료에 따르면 GUI에서 ByteTrack, OC-SORT, BoT-SORT를 선택할 수 있습니다. GUI가 보내는 것은 추적기 번호이고 Runtime은 카탈로그에서 해당 설정을 찾습니다. 새 추적기를 생성한 뒤 다음 프레임 경계에서 교체합니다. 접수 응답과 완료 응답을 구분해 변경 결과를 확인하고, 생성 실패 시에는 기존 추적기를 유지합니다. 이 장은 GUI와 Runtime 사이의 요청·응답 경계를 설명하며, 세 알고리즘의 구조와 튜닝 결과는 정하건 팀원 파트에서 설명합니다. 실제 화면은 데모 앱의 캡처가 확보되면 추가합니다.

화면 진행: 추적기 번호 선택 → 프레임 경계 교체 → 접수·완료·실패 유지

## 09. 연동 및 검증 범위
전체 목차 담당 주제: 13 / 목표 60초

연동에서는 요청이 도착했다는 것과 실제 변경됐다는 것을 구분해서 확인합니다. 팀원 자료의 접수·완료 응답과 생성 실패 시 기존 추적기 유지가 그 기준입니다. 성능 비교에서 기본 추천은 BoT-SORT이며, OC-SORT는 ID 변경과 재현율에 강점이 있어 함께 남겼습니다. 비교 조건과 세부 수치는 추적 알고리즘 파트에서 설명합니다. 최종 시연에서는 실제 앱과 선택한 추적기, 교체 후 ID 처리, 영상 설정을 맞추고 동작과 계측 결과를 확인합니다. 이번 자료 개정은 팀원 제공 문서에 따른 것으로, 제가 장치 시험을 새로 수행한 결과는 아닙니다.

화면 진행: 변경 성공 → 실패 유지 → 최종 설정·측정
